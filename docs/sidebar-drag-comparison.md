# 分栏拖动与原版的同尺寸对比

本表记录修正前的差异；后续已对齐列表拖动下限和窗口缩放，保留我们的宽度记忆，结果见 [分栏对齐记录](sidebar-alignment.md)。

2026-11-11，原版下载包 **妙言 4.8.0** 默认 AppKit 窗口，对比我们的 macOS 原生窗口。通过真实鼠标拖动和辅助功能分隔线读数测量，没有修改产品代码或输入笔记正文。

主测试窗口均为 **1120×780pt**，2×截图均为 **2240×1560px**；多数对照从文件夹 200、列表 280 开始。另做 1000、960 宽度对照。本文数字使用原生逻辑点／Web CSS px，不使用截图物理像素。

## 已一致的部分

- 文件夹最大 280；90 可以停住，86 吸附到 0，只留下列表。
- 文件夹已隐藏时，列表最大 600；向左小于 180 可以收起列表。
- 用 ⌘2 收起 300 宽的列表再展开，两边恢复 300；⌘1 可恢复文件夹。
- 正常退出并确认进程结束后重开，再对齐窗口尺寸，两边均恢复文件夹 200、列表 300。

## 剩余差异

| 项目 | 原版实测 | 我们实测 | 原因或证据边界 |
| --- | --- | --- | --- |
| 列表拖动下限 | 拖到 219、180，松手后仍停在对应宽度 | 两者均停在 220 | 我们在 `move()` 和 `fitSidebarSizes()` 中把 220 作为拖动硬下限。原版分隔线约束只直接判断 `<180` 收起；220 还用于恢复及宽度归一化，不能据此认定拖动时也必须锁在 220。此前对这一点的理解过强。 |
| 文件夹拖动收起后的记忆 | 从 200 一次拖到 85，再按 ⌘1，恢复到本次会话此前记住的 189；重复复现 | 恢复 200 | 189 不是固定恢复值。原版同时存在 NSSplitView 自动保存和 `realSidebarSize` 恢复路径；此次恢复命中了旧宽度。我们在结束拖动时保存最新偏好。没有插桩确认原版哪一个回调未更新，不能直接断言其 `mouseUp` 未执行。 |
| 三栏中的列表收起 | 文件夹 200、列表 280，列表拖到 179：文件夹变 0，列表仍显示且变为 379；等待后仍如此，重复两次 | 两栏均收起，进入纯编辑区 | 原版文件夹已经隐藏时，同样拖动可正常收起列表，因此异常与联动路径有关。现象与外层收起后内层拖动坐标变化吻合，但未插桩确认根因，先记录为原版运行时现象，不视为既定产品规则。 |
| 窗口缩放分配宽度 | 从 1120 缩到 1000，文件夹 200→178.5，列表仍 300 | 文件夹仍 200，列表仍 300 | 原生外层分栏跟随窗口调整比例；我们保留偏好，空间不足才夹紧。继续缩到同样的 960：原版 171.5／300，我们 200／280。 |
| 窄窗口边界 | 尝试缩到 900，实际停在 960 | 可以到 900，并进入抽屉布局 | 900 的两次截图尺寸不同，已排除出同尺寸对照；重新将我们调到 960 后才记录上一行结果。原版 `AppDelegate.normalizeMainWindowFrame` 明确设置最小窗口 960×600。 |

还有一处读数差异：文件夹为 280 时，列表右侧极限原版为 358、我们为 360。原版两条独立分隔线各占 1pt，我们将边框算在栏宽中；按占位计算，编辑区起点均为 640，保留 480。因此不能把这两个原始读数直接当成编辑区相差 2px。

重启时原版窗口先回到了 1280×760，文件夹读数 228.5、列表 300；重新调到 1120×780 后回到 200／300。我们重开即为 1120×780、200／300。这属于窗口恢复策略差异，不能将未经重新对齐的宽度当作分栏记忆丢失。

## 归属与验证边界

我们自己的处理归属 [sidebar-layout.ts](../src/sidebar-layout.ts) 和 [sidebar-resize.ts](../src/sidebar-resize.ts)。原版静态对照为 `Views/EditorSplitView.swift`、`Views/SidebarSplitView.swift`、`Controllers/ViewController+Layout.swift` 及 `Controllers/AppDelegate.swift`；源码用于解释路径，实际行为以上述 4.8.0 运行包为准。

对比中另一个会话将我们的运行包切换到 `artifacts/multiwindow-20261111/MiaoYan Editor.app`。核对 `sidebar-layout.ts`、`sidebar-resize.ts`、`sidebar.css`、`sidebar.ts` 和 `index.html` 的构建输入哈希，五项均与上一轮包一致；重新连接当前进程后继续，没有回退另一个会话的功能。[二进制、输入哈希和分项数值](../artifacts/sidebar-drag-comparison/verification.json)

验证方法修正：上一轮测试证明了我们定义的规则能工作，不能单独证明与原版一致。分栏对齐后续应分别验证“拖动约束”“松手后的宽度”“拖动收起”“快捷键收起”和“恢复读取的宽度”，并先确认窗口尺寸一致；应用进程切换后重新绑定，避免继续控制旧进程。

本轮未改产品代码，未逐帧测动画时长，未测试其他桌面系统或手机。结束时两边保持 1120×780、三栏展开、宽度 200／300，我们的当前版本保持前台运行。
